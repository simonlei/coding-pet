Grounding Context — Codebase Snapshot

项目形态：Go 1.25+ 项目，两个二进制 cmd/agent（每台开发机） + cmd/server（中心，内存 Store，无 DB，90s→offline / 24h→evicted），加一个 ~1355 LOC 的 Android WebView 客户端和 951 行内嵌 vanilla-JS 前端。四类采集：CodeBuddy CLI（PID + JSONL 尾部反扫）、CodeBuddy IDE（history/ mtime 衰减，Linux 静默跳过）、WorkBuddy（只读 SQLite）、Claude Code（事件驱动 status/waitingFor）。

近期方向：7 月 10 日一口气落地了 internal/notifier（Detector + Dispatcher + Target + Redact，~1700 LOC），主打企业微信群机器人推送；Dispatcher 接口 + kind 字段为 dingtalk / lark / slack / 通用 webhook 预留。前后紧跟着 Android 自更新、跨境网络的 30 min 超时、跳过 android-v* tag、以及 Claude Code 的 idle → waiting_for_input 语义对齐。前沿明显在「主动 push 通道」和「更精细的空闲/等待判定」这两根线。

可见杠杆点：Server 无 DB 是刻意选择；Detector.ReconcileAt 已经算出状态迁移（可复用为事件源）；~/.coding-pet/targets.json 10s 热重载是通用的 hot-config primitive，目前只服务 targets；window.CodingPetHost JS→Native 桥今天只用了 setAlert(count)；SessionInfo.ContextTokens 已从后端一路传到前端但 UI 里没用；TOOL_LABELS 在 index.html:821-825 漏了 codebuddy_ide（现存 bug）。

1. Reply Lane — 通知即操作台（一键回复 + 全双工桥）

Cross-cutting: F3.5 + F4.2 + F6.6 Confidence 82% Complexity M

Description. 让推送出去的那条消息本身就是一个"操作台"。企业微信 / DingTalk / Lark 全部支持带按钮的卡片消息，Slack Block Kit 更是原生的。为每次 waiting_for_approval 事件生成一条带签名的一次性回执链接（POST /api/reply/{session_id}?token=…&action=approve|reject）；server 收到后通过一个新增的 agent side-channel（TCP 长连或每 tick 的 /api/report 回执字段）把决定回带到开发机上，agent 侧再把决定灌进对应工具的 approval 通道（CodeBuddy CLI 有 subagents/*.jsonl，Claude Code 支持 hooks，WorkBuddy 走 SQLite 写回）。window.CodingPetHost 顺势从只有 setAlert(count) 变成 双向 RPC，Android 端可以直接锁屏上一键批准。

Basis · direct. internal/notifier/dispatcher.go:23-32 已经把 Dispatcher 接口 + kind 字段设计为多厂商可插拔；MainActivity.kt:201-214 的 JS↔Native 桥已经存在，只用了一个方法；internal/collector/jsonl.go:285-310 已经能识别 subagent approval 事件，说明 approval 通道本身是可写的。External. Extendo (egradman/extendo-cli) 已经在做 voice-first HITL 的相同故事；Cursor Cloud Agents 从 iOS/Android/Slack 起会话。Reasoned. 目前 push 是单向的：user 收到通知 → 走到笔记本前 → 按一下 → 才继续。这个"走过去"是 8pm 后所有等待时间的中位数来源；把它压到 0 秒的路径已经全部具备。
Rationale
把产品从「监控器」变成「遥控器」。494 个 fleet 仓库里几乎没有做到这一层的（Cursor Cloud 只在 web），加上你已经有的 Android + 中国生态 push 通道（企微），这是最容易做出差异化的一步。
Downsides
签名 token 的重放/伪造攻击面变大（HMAC + 30s TTL + per-session single-use 足够）；agent 侧需要新增一个「等待远程决定」的中间状态，否则重复回执会错乱；不同工具的 approval 通道形状差异大，一期先做 Claude Code hooks 最干净。

Meeting test. "手表上批准了 git status——这一秒起，coding-pet 就不再只是通知栏。"

2. Event Bus 底座 — SSE 推送 + 追加式历史，替代 1s 轮询

Cross-cutting: F4.6 + F1.7 + F3.2 Confidence 88% Complexity M

Description. 停止对 Store 做每秒一次的全量 deep-copy 轮询。把 Detector.ReconcileAt 已经算出来的状态迁移（transition 事件）、每次 /api/report 里带来的心跳 diff，统一进一条带单调 seq 的追加式内存 ring buffer（24h 上限、可选落一份 WAL 到 ~/.coding-pet/events.jsonl）。前端浏览器订阅 GET /api/events?since={seq}（SSE）、notifier 订阅同一条流、Android 也订阅同一条；三个消费者一个源。副产品：?since= 换来天然的 「昨晚 8 点到现在这台 box 发生了什么」 回放能力，无需引入外部 DB。

Basis · direct. internal/server/store.go:82-97 「deep-copies every dashboard read (O(n) per 1s poll — the busy loop)」；internal/notifier/detector.go:105-187 「single-shot armed baseline + 5s debounce + 60s GC」已经在计算状态迁移事件；internal/notifier/target.go:187-252 10s 热重载已经是 hot-config primitive，语义上就是 pub-sub 的第一个消费者。项目里说的「no historical view (no DB)」在 grounding 里被标为一个 gap。Reasoned. 一条事件流服务三个消费者，比"三个消费者三个私有轮询"少一个数量级的 CPU；?since= 让「重启不丢通知」和「回放调 detector bug」全都免费。
Rationale
这是"1 个决策解锁 5 个未来功能"的经典 leverage 动作。历史查询、SSE、Android 推、notifier 规则化、回放调 bug 全部落在同一个基础设施上。它是 Idea 3 / 5 / 7 的公共前提。
Downsides
需要设计 seq 的分配（谁分配、如何 monotonic across restart，简单方案：内存自增 + 启动时 time.Now().UnixMicro() 抬底）；WAL 可选功能会增加文件写入压力；SSE 在企业代理下偶尔不稳，需要一条 fallback 到 long-poll。

Meeting test. "我们那个 store.go 里的 deep-copy busy loop 现在没了；顺手加了 /api/events?since=——所以昨晚断线的机器一上线就能接着放。"

3. 通知升级阶梯 + 路由规则引擎（Andon-style）

Cross-cutting: F1.1 + F3.7 + F2.7 Confidence 85% Complexity M

Description. 目前 Detector 单次触发单次推送、5s debounce、无分级。给它加两件事：(a) 时间分级的升级阶梯 —— 5s 软 ping → 60s 复发 → 5min「stalled」响铃，靠现有的 60s GC 记账即可实现；(b) 把 targets.json 从静态 fanout 变成一个规则引擎（targets.d/*.json），写规则："IF waiting_for_input AND workhours THEN slack; IF unresponded > 10min THEN escalate; IF value_velocity_collapse THEN team_channel"。(c) 附赠：把 5s debounce 从"等 5 秒确认后才发"翻转成"立刻发，5 秒内 flap 则 edit 消息为 '误报，撤销'"——企微、飞书、Slack 都支持消息编辑；中位延迟从 5s 掉到 ~1s。

Basis · direct. internal/notifier/detector.go:105-187 现有 5s debounce + 60s GC + 稳定跃迁语义；internal/notifier/target.go:158-183 的 atomic tmp+rename、0700/0600 权限、10s 热重载已经是规则文件的合适底座；internal/notifier/dispatcher.go:23-32 保留了 kind 字段。External. PagerDuty / Opsgenie 全是规则引擎；Toyota Andon 的分级灯柱是这一类 UX 的 canonical 原型；claude-fleet 显式列了 stalled(5+min) 桶但没做升级 —— 你可以做到。Reasoned. 一次推送对"等 5s 就走开的人"和"忙别的忘了 30 分钟的人"是同一响应；把它变成"越等越大声"符合真实的注意力衰减。
Rationale
「等 5s 才推」是当前设计里最贵的一个决定 —— 它默认所有等待都值得延迟。翻转成"立即推 + 撤回"是把延迟主动收敛到 1s。规则引擎则把每个用户都会问的"别在开会时炸我"变成一行 JSON。
Downsides
消息 edit 语义需要每个 dispatcher 单独实现（wechat_work 支持有限）；规则引擎会滋生自己的一套小 DSL —— 一期只做布尔字段匹配，别过早引入表达式解析器；升级阶梯里的"stalled"要区分开"agent 停了"和"人忙别的"，不然它会变成新的噪音源（见 Idea 7 的 PAR）。

Meeting test. "我不再解释 debounce 是 5s 还是 1s —— 这个字段现在是 ~/.coding-pet/targets.d/default.json 里的一行。"

4. ARP 协议 + Collector SPI — 从 scraper 变成 hub

Cross-cutting: F3.1 + F4.3 + F6.3 + F4.8 Confidence 68% Complexity L

Description. 今天四个 collector 分别 reverse-engineer 四种私有磁盘格式：JSONL 尾扫 + logstate 修正、history/ mtime 衰减、SQLite LEFT JOIN、Claude Code 事件字段。发布一个小小的公开线协议 ARP（Agent Reporting Protocol）：agent 只接 POST /api/event 的 JSON 帧，schema 就是 SessionInfo。原来的四个 collector 变成"参考实现"或"降级 fallback"；同时开一个 Collector SPI：~/.coding-pet/collectors/*.toml（或者更激进地直接是 shell/py 子进程，stdout 吐 JSON），社区能加 Aider / Cline / Cursor / Codex CLI 而不改 Go 代码。顺带修 TOOL_LABELS bug：前端 /api/collectors 拉 manifest（label/icon/allowed states/context-tokens-cap），不再硬编码。

Basis · direct. internal/collector/codebuddy_ide.go:134 「Linux 静默跳过」是 hard-coded collector 的直接代价；internal/server/index.html:821-825 缺少 codebuddy_ide 是硬编码的现存 bug；internal/collector/jsonl.go:86-129 reverse-tail 逻辑 stuck inside 一个 collector。External. Claude Code 有 hooks API（Notification / SubagentStop）；MCP 的推广也在朝"每个 agent 用统一 wire 汇报"这个方向走。Reasoned. 现在每个新工具的支持成本是"读一遍它的私有磁盘格式 + 加个 collector.go + 在 index.html 里加 label"。发布一个小协议后，这个成本降到 "在你的 agent 里 curl 一下"。
Rationale
把产品定位从"scrape 每家的 JSONL"变成"每家来我这里报到"。在 494 个 fleet 仓库的竞争里，谁先立住"多厂商中立的观测标准"，谁就是那个没人想 fork 的地基。副作用是彻底解掉 Linux IDE 支持——用户自己写 20 行 bash 就行。
Downsides
协议要谨慎，一旦发布就得管兼容性（SessionInfo 目前有 idle_ms/context_tokens/status/waiting_for，尚可）；一期即使发布也没有厂商会立刻接入，短期收益主要来自"自己写的 cron / Makefile / Python 脚本能进 dashboard"；Confidence 打 68% 是因为这个动作的短期回报最小、长期回报最大。

Meeting test. "有人在 Aider 里加了 5 行 curl，就能看见它出现在 dashboard 上——完全没碰任何 .go。"

5. 按项目/任务分组：机器降为元数据

Cross-cutting: F3.3 + F5.8 Confidence 78% Complexity S

Description. 今天前端按 machine_id 分块。但当我在两台 laptop 上都跑 Claude Code 改 payments/checkout 时，它是"一件事"，不是"两台机器"。改成主轴 = (git_repo, cwd, active_branch)，机器名降级为卡片右上角的小 chip。前端在 12+ session 时可以再加一层「区首席」：以项目为分组头，头部显示分组最坏状态（"billing · 5 sessions, 1 等待审批"），点开展开。手机端只显示"首席层"，一眼扫完全部工作。SessionInfo 已经带 CWD，CodeBuddy IDE 里还用 "Workspace Folder:" 反查过，分组 key 免费。

Basis · direct. internal/protocol/types.go:34-48 里 SessionInfo 已经带 CWD；internal/collector/codebuddy_ide.go 的 parseWorkspaceFolder（:283-295）已经反查过工作区，可复用；internal/server/index.html:820 前后的 grid 布局全是硬编码的 machine 层级。Reasoned. 「多机 + Android」是你相对 494 个 fleet 仓库的稀缺护城河（外部研究）；但当前 UI 把机器放在最外层，恰恰把这个卖点埋起来了。三台机器都在改同一个 refactor，用户想看的是 refactor 的状态，不是"这台机器上有一个 session"重复三遍。
Rationale
成本极低（前端排序 + 分组渲染），价值感极高（一眼扫 4 个项目 vs 一眼扫 17 个 tile）。也把 Android 端从"和桌面一样的小格子"变成天然的"首席层"—— 手机就应该只看 4 行。
Downsides
无 CWD 的 session（Claude Code 有时候是空的）需要 fallback 到"未分组"；用户手动指定分组的欲望以后会来（"这 3 个 session 是同一个功能不同分支"），先不做，靠 CWD 覆盖 80%。

Meeting test. "手机上打开只看到 4 个项目卡，其中一个红了 —— 而不是 17 个 tile 里找那个红的。"

6. 首条消息 Purpose 面包屑

Single (F1.2) Confidence 92% Complexity S

Description. 每张 session 卡片除了工具/状态/上下文 token，加一行副标题："refactor auth to JWT"、"fix flaky login test"。做法：codebuddy_ide.go:283-295 已经 grep 过第一条 user message 的开头（为了拿 "Workspace Folder:"），把同一次 read 顺手截取首句自然语言即可；CodeBuddy CLI 的 JSONL 头部有 messages[0]；WorkBuddy 有 sessions.first_message；Claude Code 的 session 目录里 *.json 有 title 字段。零新读、零 LLM、只加一个 SessionInfo.Purpose string。

Basis · direct. internal/collector/codebuddy_ide.go 的 parseWorkspaceFolder 已经在 grep 首条 user message；internal/protocol/types.go:34-48 加字段无破坏性；internal/server/index.html:720-724 显示层加一行是纯 vanilla-JS。External. claude-fleet 的定位文案明确列出 "forgotten session purposes" 为它解决的用户痛点。Reasoned. 你手机屏幕上 8 张卡片，都写着 "claude / waiting / 74k tokens"—— 你根本不知道该管哪张。首句自然语言是最便宜的信息。
Rationale
成本几乎为 0（一个字段 + 一个 grep + 一行前端），收益是"我知道 box-3 上那台在干什么"。Confidence 92% 是因为四个来源都已经有首句可读，几乎没有实现风险。
Downsides
隐私：首句可能包含敏感内容（客户名、API key），要有一个 --no-purpose flag；截断策略需要选（40 字够短、够扫）；对没有 user message 的空 session 要 fallback 到 "<new session>"。

Meeting test. "手机上 8 张卡片，我一眼看出 box-3 是我 20 分钟前起的那个 refactor —— 而不是猜。"

7. 主动 PAR 心跳：静默 Agent 告警

Cross-cutting: F5.3 Confidence 72% Complexity M

Description. 今天的判活是"90 秒没收到 /api/report 就 offline"——但 agent daemon 活着、上报正常、里面挂着的 Claude CLI 却卡死了 这种最讨厌的状态是看不出来的。借消防的 PAR（Personnel Accountability Report）思路：agent 侧每 60s 主动对每个 session 做一次「你还在吗」的可观测验证 —— 对 CodeBuddy CLI 是"最后一条 JSONL 行是否在合理窗口内"，对 Claude Code 是"进程存活 + 最近有 stdout/stderr 活动"，对 IDE 是"file mtime 是否移动"。三次 PAR 无响应 → 触发一个新的状态 unresponsive_but_alive，不同颜色、不同响铃、不同 dispatcher（这是没有人来的告警，语义比 waiting_for_input 更急）。

Basis · reasoned + direct. 现有 internal/collector/claudecode.go:99-113 只看 status/waitingFor，一旦 Claude CLI 自身 hang，status 就冻结在 working——90s→offline 完全触发不了；internal/server/store.go:11-16 的 offline 判定基于 machine 层（agent 上报中断），不是 session 层（工具进程停顿）。External. Claude CLI 挂起是社区里公认的现象（Warp/Ghostty 里的 OSC 通知也是为此而生）。消防的 PAR 是这类"沉默失败"的 canonical UX：区分「等我」和「无人回应」。Reasoned. 你今天有 两个失联信号（machine offline, session waiting）；引入 第三个 —— session 静默但 agent 活着 —— 覆盖真实存在但目前隐形的失败模式。
Rationale
「等你 30 分钟」和「卡死 30 分钟」是两种截然不同的用户体验 —— 一个是我的错，一个是工具的错。把它们分开，才知道该开新会话还是继续等。
Downsides
PAR 判定的假阳性成本高（错误的"你死了"通知会侵蚀信任），一期用保守窗口（3× 平均活动间隔）；对 WorkBuddy 这类无 PID 的工具没有干净的 PAR 通道，先跳过。Confidence 72% 是因为每个工具的"活性验证"信号不完全对称。

Meeting test. "我的 Claude CLI 卡了 40 分钟没人告诉我 —— 现在 30s 内 coding-pet 就报了；而且它显然不是 waiting，是 dead。"

Cross-Cutting Threads (未进 top 7 但值得留意)

Attention Model

Frame 5 的三个想法（Radiology STAT 分级、Sonar Ambient/Designated/Tracked 晋级、Chess flag-fall + board-order）在骨子里是同一件事：不是所有 session 都同等重要。可以叠加成一个未来的"注意力模型"—— 每个 session 有 tier + 自声明回复预算 + 项目排序。今天先不做，等 Idea 5（按项目分组）落地后自然浮现。

Local History / Flight Recorder

Idea 2 的 event bus 已经天然带上了 24h 回放能力；如果再落一份 WAL 到 ~/.coding-pet/events.jsonl，就有了 「昨晚发生了什么」的能力。当社区最爱问的 "为什么这个 session 突然停了" 反复出现时，这个 WAL 就该开。可以先放着，工作量极小。

Morning Digest

如果有了历史（上一条），可以在 Android 端做一个"早晨第一次解锁"的 briefing 卡：过去 12h 里哪些 session 等待最久、哪些烧了最多 token、哪些卡死过。比一晚上叮叮咚咚推送更符合"睡了一觉再来处理"的实际节奏。
